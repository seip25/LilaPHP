LilaPHP Framework

A lightweight, modular, and performance-first PHP micro-framework designed for simplicity, flexibility, and security. Install in seconds with Composer, runs on any server (Nginx, Apache, LAMPP, XAMPP, WAMP, FrankenPHP, Swoole), and combines the power of React Islands + Twig for modern, hybrid applications.

Note: Starting from v1.4, LilaPHP uses a clean root structure. After installing via Composer, run php cli.php init to generate the scaffolding.

Why Choose LilaPHP?

LilaPHP avoids the monolithic approach of traditional frameworks. Instead of loading a massive global state, LilaPHP instantiates only what is required for the specific request. No complex setup—just run composer create-project and you're ready to go.

This means faster cold starts, lower memory usage, and the ability to run multiple "micro-apps" within the same codebase—each with different security policies, headers, or middleware configurations.

Universal compatibility: Works seamlessly on Nginx, Apache, LAMPP, XAMPP, WAMP, FrankenPHP, Swoole, VPS, shared hosting, or PHP's built-in server. Deploy anywhere without configuration headaches.

app/index.php 
include_once "./LilaPHP/index.php";
use Core\App;

// Standard App
$app = new App(); 

// Admin Panel (Strict Security)
$adminApp = new App([
    'security' => ['cors' => false, 'sanitize' => true,'logger'=>false,'rateLimit'=>30],
     'translate'=>true
]);

// Public API (Open Access)
//rateLimit 300 request for 1 minute per IP address
$apiApp = new App([
    'security' => ['cors' => true, 'rateLimit'=>300],
    'translate'=>true
]);

Installation

Get started in under 60 seconds with Composer. No complex configuration, no build steps required.

1. Install with Composer 

                            composer create-project seip25/lila-php LilaPHP

2. Initialize Scaffolding

Run the initialization command to copy templates and assets to your project root. 

                            php cli.php init

3. Edit URL_PROJECT in .env

3. Start the Server

Option A (Recommended): Visit http://localhost/LilaPHP directly with LAMPP, XAMPP, WAMP, Nginx, or Apache. Works out of the box and supports language-prefix routing via .htaccess!

Option B: Use PHP's built-in server (development only): 

php -S localhost:8000

Note: The built-in PHP server does not native support virtual language routing (e.g. /es/index.php) without a custom router script. For testing SEO and Localization, please use a full server like Apache or Nginx.

React Integration

New

Combine the best of both worlds: server-side rendering with Twig and interactive React components using the Islands Architecture pattern. Mount React islands anywhere in your Twig templates, or render full React pages. Enjoy Hot Module Replacement (HMR) during development and optimized builds for production.

Development 

npm install
npm run dev

Starts HMR server at port 5173

Usage in Twig 

<!-- base.twig (Standard for all pages) -->
<head>
    <!-- Injects only the Vite client for Twig/Static HMR -->
    {{ hot_reload() }}
    {% block extra %}{% endblock %}
</head>

<!-- your_react_page.twig -->
{% block extra %}
    <!-- Injects React Refresh runtime + Main entry point + CSS in production -->
    {{ vite_assets() }}
{% endblock %}

{% block content %}
    <!-- Mount a React Component -->
    {{ react('Header', {'user': {'name': 'Lila'}}) }}
    
    <main class="p-4">
        <h1>Standard PHP Content</h1>
        {{ react('Counter', {'start': 10}) }}
    </main>
{% endblock %}

Note: Starting from v1.4, all npm commands and configurations are located in the project root.

Re-rendering React Islands

You can trigger a re-render of your React islands from standard JavaScript (e.g., from Twig templates, jQuery, or other non-React components) using the global function window.renderReactComponent(name).
This is useful for updating components that rely on shared client-side data like localStorage from other independent DOM elements without needing a complete page reload. 
// Re-render all React components on the page
renderReactComponent();

renderReactComponent('CartBadge', 'component');
// Re-render a specific full page component
window.renderReactComponent('ReactExample', 'page');

Twig & PHP Hot Reload

LilaPHP natively supports Full Hot Reload for all your Twig templates and PHP core configurations without any extra tools.
Because Vite acts as the development server watching your app/resources folder, when you modify files like index.twig or base.twig, a WebSocket signal is automatically broadcasted to the browser forcing a full page reload instantly.

Comparison:
• hot_reload(): Only the HMR client. Best for Twig-only pages to keep the source clean.
• vite_assets(): Includes hot_reload() PLUS React Refresh and your entry scripts. Mandatory for React islands.

React pages templates

This way you can use React to load directly from resources/js/pages, in case you want to use React directly without templates with Twig, passing the context directly. Lila creates the "HTML", with scripts, styles, meta tags, langs, body and the main React component.
Important Note about Rendering: LilaPHP uses different data attributes to separate the rendering of full pages and standalone components (islands).
- When using $res->renderReact(), it mounts a data-react-page="ComponentName".
- When using Twig's react('ComponentName') helper, it mounts a data-react-component="ComponentName".
In your main.jsx, renderReactComponent('all', 'component') or renderReactComponent('all', 'page') uses these attributes to know exactly where to import and mount them from (components/ or pages/).

SPA Support

Native

LilaPHP features a powerful, built-in Single Page Application (SPA) engine that enables instant, seamless transitions between Twig-rendered pages and React-based interactive components.

Hybrid Navigation

Intercepts internal links and performs partial DOM updates using JSON payloads. It combines server-side security (session validation, CSRF) with frontend speed.

Intelligent Resource Loading

Automatically extracts and re-injects missing scripts or styles into the <head>, ensuring dynamic dependencies (like Vite modules) load only when needed.

How to enable

<!-- 1. Use the main content container in base.twig -->
<main id="lila-spa-content">
    {% block content %}{% endblock %}
</main>

<!-- 2. Use the dynamic layout in your templates -->
{% extends layout | default("base.twig") %}

Auto-wiring Dependency Injection

New

LilaPHP automatically resolves your route handler dependencies using Reflection. This means you no longer need global $app; or to pass specific arguments manually. 

use Core\Response;
use Core\Session;
use Core\Config;
use Core\Database;

#[GET]
function showDashboard(array $req, Response $res, Session $session) {
    // The framework detects that you need the Request array, Response object, and Session.
    // It automatically injects them without any extra work.
    
    if (!$session::has('user')) {
        return $res->redirect('/login');
    }
    
    return $res->render('dashboard');
}

#[GET]
function showDashboardWithConfigAndDB(array $req, Response $res, Config $config, Database $db) {
    // $db is automatically instantiated using configuration from app/.env by default
    $pdo = $db->getConnection();
    $insert = $pdo->prepare("INSERT INTO users (name, email, password) VALUES (?, ?, ?)");
    $random = rand(1, 100);
    $email = "Jhon{$random}@email.com";
    $insert->execute(['John Doe', $email, 'password']);
    $query = $db->query("SELECT * FROM users");
    $users = $query->fetchAll(PDO::FETCH_ASSOC); 
    
    
    $debug = $config::$DEBUG;
    $urlProject = $config::$URL_PROJECT;
    
    return $res->render('dashboard');
}

use Utils\EmailService;

App Core

The App class is the heart of LilaPHP. It initializes configuration, handles routing, executes middleware, and manages responses. 

$app->translate('hello'); // return key 'hello' in current language
$app->getEnv('DEBUG'); //return the value of the environment variable DEBUG

Core Classes

LilaPHP provides several static and instantiable core classes to handle common tasks like configuration, sessions, databases, logging, and security. You can use their static methods globally or auto-wire them directly into your route handlers.

Config & Session

The Config class gives you access to your .env variables via static properties, while Session handles secure, encrypted session management.

Static Usage

use Core\Config;
use Core\Session;

// Access config values statically
$isDebug = Config::$DEBUG;
$dirProject = Config::$DIR_PROJECT;

// Manage sessions statically
Session::set(key:'user_id', value:123,encrypt:true);
if (Session::has(key:'user_id')) {
    $userId = Session::get(key:'user_id');
}
Session::remove(key:'user_id');
Session::destroy();

Auto-wiring Injected Usage

You can inject these core classes directly into your route endpoints. LilaPHP will automatically resolve and inject them. 

use Core\Config;
use Core\Session;
use Core\Response;

#[GET]
function get(array $req, Response $res, Session $session, Config $config) {
    if (!$session::has('auth')) {
        return $res->jsonResponse(['error' => 'Unauthorized'], 401);
    }
    
    // Access non-static methods or static properties
    $baseUrl = $config::$URL_PROJECT;
    $version = $config::$VERSION_PROJECT;
    
    return $res->jsonResponse([
        'user' => $session::get('auth'),
        'api_version' => $version
    ]);
}

Database & Logger

The Database class manages PDO connections and retries, while Logger handles writing application logs easily. 

use Core\Database;
use Core\Logger;
use Core\Response;

#[POST]
function createUser(array $req, Response $res, Database $db, Logger $logger) {
    try {
        $pdo = $db->getConnection();
        $stmt = $pdo->prepare("INSERT INTO users (name) VALUES (?)");
        $stmt->execute([$req['name']]);
        
        $logger::info("User created successfully: " . $req['name']);
        
        return $res->jsonResponse(['success' => true]);
    } catch (\Exception $e) {
        $logger::error("Failed to create user: " . $e->getMessage());
        return $res->jsonResponse(['error' => 'Database error'], 500);
    }
}

Security & Translate

Security offers methods for CSRF, sanitization, hashing, and more. Translate handles easy translation lookup. 

use Core\Security;
use Core\Translate;
use Core\Response;

#[GET]
function secureEndpoint(array $req, Response $res, Security $security, Translate $translate) {
    // Generate a secure hash
    $csrf = $security::generateCsrfToken();

Auth Attribute

Security

Secure your routes declaratively using the #[AUTH] attribute. It automatically verifies session existence and validity before executing your handler.

Basic Usage

By default, the attribute will look for the "auth" session key and redirect to /login if not found. 

use Core\{GET, AUTH, Response};

#[GET]
#[AUTH] // Uses defaults: key="auth", redirect="/login" 
//#[AUTH(key: "mykeyAuth",redirect:'/')]
//save with encrypt session ,example Session::set("auth",$myUserAuth,true) or $session::::set("auth",$myUserAuth,true)
function dashboard($req, Response $res) {
    return $res->render("dashboard");
}

Parameters:

  • key: The session key to check (default: "auth").
  • decrypt: Whether to decrypt the session value (default: true).
  • redirect: URL to redirect if check fails (default: "/login"). Set to false to return a 401 Unauthorized status instead.

🚀 Performance Tip:

Auth attributes are fully compatible with LilaPHP's route optimization system. When you run php app/cli.php app:optimize, the authentication logic is pre-compiled for maximum performance in production.

Middleware

LilaPHP includes a built-in middleware system that allows you to execute code before and after your routes are executed.Or you can add middleware to a specific route and method. 

include_once "./app/index.php";
use Core\BaseModel;
use Core\Field;
use Core\App;
use Core\Response;

$app = new App();
class LoginModel extends BaseModel
{
    #[Field(required: true, format: "email")]
    public string $email;

    #[Field(required: true, min_length: 6)]
    public string $password;
}
$lang = $app->getSession(key: "lang", default: "es");

$app->post(
    callback: function ($req, $res) use ($app, $lang) {
        return $app->jsonResponse(["success" => true, "login" => false, "session" => $lang]);
    },
    middlewares: [
        fn($req, $res) => new LoginModel(data: $req, lang: $lang), 
        //Middleware for "/login" post method with validation BaseModel
    ],
    csrf: true
);

//Or use with attributes
use Core\Middleware;

function testingMiddleware($req, $res) {
    error_log(message: "Testing middleware");
}

function testingMiddlewareRepeat($req, $res) {
    error_log(message: "Testing middleware repeat");
}

#[GET]
#[Middleware('testingMiddleware')]
#[Middleware('testingMiddlewareRepeat')]
function login($req, Response $res) {
    global $app;
    $lang = $app->getSession(key: "lang", default: "es");
    return $app->jsonResponse(["success" => true, "login" => false, "session" => $lang]);
}
$app->add(callback:"login");

//Global middlewares after and before for "/login" all methods in route
$app->addMiddlewares(middlewares: [
    'before' => [
        fn($req, $res) => error_log(message: "Custom before route")
    ],
    'after' => [
        fn($req, $res) => error_log(message: "Custom after route")
    ]
]);

$app->run();

New

You can declare middlewares directly using attributes on your route methods or functions.

Event Dispatcher

New

LilaPHP includes a very lightweight, memory-based event bus that helps you decouple your application's logic. You can listen to custom events and trigger them from anywhere in your code.

Example Usage 
use Core\Event;

// 1. Register a listener (e.g., in App constructor or a dedicated provider)
Event::listen('user.registered', function(array $userData) {
    // Send a welcome email, update analytics, etc.
    Logger::info("New user registered: " . $userData['email']);
});

// 2. Dispatch the event from a controller or model
Event::dispatch('user.registered', ['id' => 1, 'email' => 'hello@example.com']);

Background Queues (Workers)

New

Offload heavy processing like sending emails or resizing images to background workers. The Queue system stores pending jobs in the database and a CLI worker daemon continuously consumes them.

1. Create Job Handler 

namespace Jobs;

class SendEmailJob {
    public function handle(array $payload) {
        $to = $payload['to'];
        // logic to send email...
    }
}

2. Push to Queue 

use Core\Queue;

Queue::push(Jobs\SendEmailJob::class, ['to' => 'user@domain.com', 'subject' => 'Welcome']);

3. Run the Worker

Start the worker daemon in your terminal (or via a process manager like Supervisor/systemd in production): 

php app/cli.php queue:work

Micro-ORM Integration

New

LilaPHP's BaseModel provides an Active Record style ORM. Using this Micro-ORM is entirely optional — you can always fallback to standard PDO methods if you prefer raw SQL. However, using Models allows you to abstract simple queries, relate entities gracefully, and automatically validate data.

Defining Models & Schema

Models act as both a data validator (with `#[Field]`) and a schema definer. The `#[FieldDatabase]` attribute sets the table column rules. Note: these attributes are scanned by the CLI tool to automatically generate and migrate your database tables (detailed in the CLI & Migrations section below). 

//app/models/User.php
namespace Models;

use Core\BaseModel;
use Core\FieldDatabase;
use Core\HasMany;

class User extends BaseModel {
    #[FieldDatabase(type: 'int', primaryKey: true, autoIncrement: true)]
    protected int $id;

    #[FieldDatabase(type: 'varchar', length: 255, unique: true)]
    public string $email;
    
    #[FieldDatabase(type: 'boolean', default: '1')]
    public bool $is_active = true;

    // Define relationships with modern PHP Attributes
    #[HasMany(model: Post::class, foreignKey: 'user_id', localKey: 'id')]
    public array $posts = [];
}
  //app/models/Post.php
 
namespace Models;

use Core\BaseModel;
use Core\Field;
use Core\FieldDatabase;
use Core\BelongsTo;

class Post extends BaseModel
{
    #[FieldDatabase(type: 'int', primaryKey: true, autoIncrement: true, unsigned: true)]
    protected int $id;

    #[Field(required: true)]
    #[FieldDatabase(type: 'varchar', length: 255)]
    public string $title;

    #[Field(required: true)]
    #[FieldDatabase(type: 'text')]
    public string $content;

    #[FieldDatabase(type: 'int', unsigned: true)]
    public int $user_id;

    #[FieldDatabase(type: 'boolean', default: '1')]
    public bool $is_active = true;

    #[BelongsTo(model: User::class, foreignKey: 'user_id', ownerKey: 'id')]
    public ?User $author = null;
}

Querying & Relationships

Queries automatically exclude logically deleted records (where is_active = 0) unless overridden. You can also eagerly load relationships defined with #[HasMany], #[HasOne], or #[BelongsTo] using the `with` parameter. 

// Fetch by primary key (Automatically appends AND is_active = 1)
$user = User::find(1);

// Query with condition (Excludes logically deleted records automatically)
$activeUsers = User::where('status', '=', 'verified');

// Fetch all records (includes activeOnly filter)
$allUsers = User::all();

// You can bypass the active filter by passing activeOnly: false
$userWithDeleted = User::find(1, activeOnly: false);

// Logical Deletion Practice (Sets is_active = 0 instead of executing DELETE)
// This preserves referential integrity and audit logs securely.
$user->delete(logic: true);

// Eager Loading Relationships (Using 'with' hydrates your nested dependent models)
$userWithPosts = User::find(1, activeOnly: true, with: ['posts']);
// $userWithPosts->posts now contains an array of Post instances connected to the user

Note: When using $app->getDatabaseConnection() without parameters, it uses the database configuration defined in app/.env. If no configuration is found, it defaults to SQLite.

Creates the database (if it doesn't exist) and runs all pending migrations. This is the recommended command for initial setup.

What it does:
  • Creates database if it doesn't exist (MySQL/PostgreSQL only)
  • Scans app/ for models extending BaseModel
  • Creates tables from model FieldDatabase attributes
  • Records migrations in migrations table
migrate:run

Runs migrations only if the database already exists. Use this when the database is already created. 

php app/cli.php migrate:run
Use case: When database exists but tables need to be created or updated.
migrate:status

Shows the current migration status for all models. 

php app/cli.php migrate:status
Output example: 
✓ posts (from Models\Post)

migrate:fresh Destructive

Drops all tables and re-runs migrations. ⚠️ This will delete all data! 

php app/cli.php migrate:fresh
Use case: Development environment when you need to reset the database completely.

Warning: You will be prompted to confirm with "yes" before execution.

migrate:rollback In Development

Rollback functionality is currently in development and not yet implemented.

Workaround: Use migrate:fresh to drop and recreate tables, or manually drop specific tables.
